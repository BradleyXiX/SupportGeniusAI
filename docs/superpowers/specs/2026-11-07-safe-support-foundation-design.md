# SupportGeniusAI safe support foundation design

Date: 7 November 2026. Status: approved by the user on 7 November 2026. Execution method: bounded Gemini/Antigravity sessions with Codex review.

## Intent, selected approach and limits

The user selected safe foundation first: keep document Q&A usable, disable live actions until a verified client workflow is designed, and address session ownership, false confirmations and operational failures. Alternative considered: implement one real client integration now; that needs a customer identity source, target CRM/order/booking system, authorization and confirmation rules, and idempotency semantics. Those decisions are deferred rather than invented.

This phase is not customer login, a multi-tenant SaaS, an admin dashboard, billing, an embedding-model migration, source-citation delivery or a finished client integration. Anonymous session ownership is not customer identity verification. Do not publish a claim that sensitive records/actions are authorized.

Keep the approved Signal desk layout, vanilla client and Express API. Frontend HEAD reviewed is 03886d2 on design/signal-desk-v1. As checked, that branch has not been pushed and no PR exists. Implement backend work on feature/safe-support-foundation from that exact reviewed local branch after a fresh Git check. Do not silently base on the older origin/main and lose the frontend. Do not merge, push or deploy in this packet. If frontend subsequently merges, reconcile the base deliberately before PR preparation.

## Deliverable

An explicitly configured Q&A/demo server that cannot dispatch real client actions; no fabricated webhook fallback; bounded, cookie-owned conversations; bounded upstream waits with safe errors; and a client that visibly reflects the actual operating mode and session state. This is a safer foundation, not certification of retrieval accuracy or production client readiness.

## 1. Explicit modes and action gate

Add APP_MODE with exactly support or demo; default support. NODE_ENV controls runtime/cookies, not permission to simulate. In support mode, use the configured provider or local Ollama; provider failure produces a stable unavailable error. Never silently fall back to simulateLLM because a key/provider is absent. In demo mode, use deterministic local fixtures only; make zero chat-provider, embedding-provider or client-webhook requests. Label every simulated chat response with an unambiguous Demo prefix. Keep pure simulation functions usable in isolated tests, not as an accidental support fallback.

Real tool execution is unconditionally disabled in this phase, irrespective of mode, CLIENT_WEBHOOK_URL, environment flags, model ACTION output or direct internal calls. Do not introduce ACTIONS_ENABLED as an escape hatch. Preserve existing tool exports only if needed for compatibility, but they must fail closed and make zero outbound webhook requests. Recognized action attempts return the deterministic chat reply: Automated actions are unavailable in this deployment. No order lookup, booking, address change or notification has been performed. Return it directly; do not ask the model to reinterpret a failure as success. Unknown/malformed ACTION/PARAMS blocks must not execute any operation or echo arbitrary tool payloads; use the same safe refusal when a tool attempt is detected.

Demo fixtures may illustrate document Q&A; they may not invent an appointment ID, SMS delivery, address change or verified order status. Remove the successful synthetic tool fallbacks and update the old tests that require them. Update promptBuilder to advertise no available actions and treat model text as untrusted. A persistent UI statement says no automated actions are performed. Model-written prose can still hallucinate; source/answer evaluation is a later scope, so do not promise zero hallucinations.

GET /capabilities is a public no-secret endpoint returning exactly the required fields {mode:'support'|'demo', actionsEnabled:false, sessionRequired:true}. It contains no keys, webhook URLs, provider credentials or session identifiers. If unavailable/malformed, the UI says configuration unavailable and never claims a live integration. Existing /health liveness/vectorStore fields remain; a 200 still does not certify the provider.

## 2. Server-owned anonymous sessions

Use express-session with a bounded, expiring store; no homemade token/signature implementation and no default express-session MemoryStore. Proposed initial store is memorystore, pinned and reviewed at implementation. Default maximum 500 sessions, 30-minute inactivity TTL, prune every minute, stale reads disabled. Store history and usage within the same server session payload, not in independent unbounded module maps. Bound history to six full user/assistant exchanges (12 entries), user messages to the existing 2000-character limit, and returned assistant text to 8000 characters with a clear truncation indication if that ceiling is hit.

This store is explicitly single-process and ephemeral: restart/eviction expires conversations; it is not durable chat storage, does not scale across workers and does not hold sensitive customer records. Document this deployment constraint. A shared/durable store is a later deployment choice. Eviction/expiry never silently revives the old conversation or lets a client choose an existing key.

Cookie defaults: HttpOnly, SameSite=Strict, Path=/, no Domain, Secure in production; production name __Host-supportgenius_session, local nonproduction name supportgenius_session. PUBLIC_ORIGIN and a SESSION_SECRET of at least 32 bytes are explicitly configured in every environment; tests use fixed nonsecret fixtures. Production requires HTTPS PUBLIC_ORIGIN and has no committed secret default. Local HTTP is allowed only outside production. Do not weaken production Secure cookies to make local tests pass. Use resave:false and saveUninitialized:false with explicit successful saves; use documented library lifecycle methods, not custom cookie codecs. Production behind a proxy must have an explicit supported trust-proxy topology; don't trust arbitrary forwarded headers from public direct access.

No authentication/session identifier is exposed to frontend JavaScript, browser storage or response JSON. The old JSON sessionId field may remain accepted/validated temporarily for compatibility, but is ignored as an authority/key. The server exclusively selects history/cost from its validated cookie. Remove the client's persistent supportGeniusSessionId storage use; chat-state generation/request IDs remain local UI correlation values only.

POST /session starts a new anonymous conversation and returns 204 after session persistence. With a valid existing session it destroys/regenerates the old server session before confirming success. It sets a fresh cookie; never return the opaque ID in JSON. POST /chat requires an initialized, unexpired cookie-owned session; otherwise return 401 with stable code SESSION_REQUIRED and no provider call. GET /health and /capabilities do not create sessions. Bootstrap/reset is rate-limited separately; chat retains its limiter.

Concurrency policy: at most one session mutation/provider request per cookie-owned session at a time, enforced server-side rather than trusting disabled browser controls. A concurrent /chat or /session request gets 409 SESSION_BUSY before any model request/history mutation; no request queue. Load/reload the current store state after acquiring ownership, and hold it through persistence. Release locks in finally; bound the lock registry and remove idle entries. Expired/destroyed/evicted sessions cannot be resurrected by an old response auto-save. Touch activity under ownership at request start, verify the same stored conversation revision still exists before committing, and suppress automatic session saving on invalidation/failure; do not return a stale Set-Cookie that can overwrite a rotated session. Tests must cover two separate HTTP agents deliberately submitting the same body sessionId, concurrent requests, expiry, reset, save failures and session-store cleanup. Use library methods and explicit ownership checks; do not leave race semantics to the builder.

## 3. Request origins and bootstrap/reset UX

PUBLIC_ORIGIN is the single first-party UI origin for this client deployment. Every POST /session and POST /chat must match its Origin exactly; absent, null or unapproved origins are rejected 403 before session/provider work. These browser-oriented APIs do not offer an unauthenticated server-to-server integration in this phase. SameSite cookies and explicit origin validation are both applied; CORS alone is not the check. Never derive the trusted origin from request Host/X-Forwarded-Host. Allow only the documented local origin in development/test; do not bypass origin checks because NODE_ENV is not production. Reject malformed JSON with 400 and oversized JSON with 413 using safe problem details.

On console load: fetch /capabilities, then POST /session with same-origin credentials; keep Send disabled with Preparing conversation until initialization succeeds. Configuration/initialization failures have clear Retry initialization control, not silent use of a browser ID. No chat request is auto-replayed. On 401, say the session expired; require explicit Start new conversation before accepting another query. On 409, show A reply is already being processed; do not retry automatically.

Backend integration changes the reset behavior deliberately: disable New conversation while the current chat request is pending. The server cannot safely treat a browser abort as proof that processing stopped. After completion/timeout, explicit reset calls POST /session and clears transcript/cost only after the server confirms rotation. While reset is pending, Send stays disabled and the button shows Starting conversation. If reset fails, do not claim history was deleted or silently post under a different conversation. Retain the previous transcript and offer Retry initialization; an uncertain reset never automatically replays chat. Continue to guard all asynchronous UI state by generation/request ownership as fixed in A7. Preserve those guards even though reset is disabled while pending, because session expiry/bootstrap races and stale tasks remain possible.

Mode disclosure is populated from /capabilities: demo says Demonstration — simulated answers, no automated actions; support says Document support — automated actions unavailable. Unknown mode does not masquerade as demo or ready support. Keep the existing accessible pending text, keyboard/IME, sanitizer fallback and reduced-motion behavior.

## 4. Bounded provider work and safe failures

Introduce a shared fetch-and-parse helper using the existing node-fetch, AbortController and documented size limit. Deadline includes reading/parsing the body, not only headers. Enforce at most 1 MiB upstream response body, 20 seconds for one LLM request, 5 seconds per embedding call, and a total /chat budget of 30 seconds. Propagate the overall abort signal through retrieval and generation; no timers clearing a different request's controller. No automatic retries. In demo mode this path is not called.

Validate the actual expected response shape before use. Empty/malformed provider output is an unavailable failure, not a successful empty reply. Do not use raw upstream bodies, URLs, keys, prompts, cookies or full customer text in public errors/logs. Catch timeout, connection, oversized-body and parse errors as a stable 502/504 problem with code PROVIDER_UNAVAILABLE or PROVIDER_TIMEOUT and a correlation/request ID. Internal logs record ID, safe category, provider label, duration and status; no transcript or credential values. Unexpected errors get a generic 500; preserve safe structured validation errors. Cap log fields and never log the Gemini key embedded in its request URL.

Maintain the existing successful /chat {reply:string,cost:string} contract. Its cost remains an estimate; no pricing/cost-accuracy redesign is included. Move per-conversation usage into the cookie-owned bounded session and reset it with rotation. Session persistence failure must not be reported as a committed successful conversation; return generic 503 SESSION_STORE_UNAVAILABLE. Readiness and model availability validation are not inferred from a key being present.

## 5. Testing, deployment and exclusions

Paid keys and CLIENT_WEBHOOK_URL are blank for all test runs. Use controlled fixtures/fake clocks and loopback provider servers. In demo mode install spies that fail the test on any provider/webhook request. Rewrite baseline route tests to create sessions/origins deliberately. Add two-agent isolation tests using the same submitted sessionId. Verify expiry/capacity, rate limits, replay/reset/concurrency, failed saves and safe cookie flags. Cross-origin and missing-origin requests must make zero provider calls.

Browser session integration tests need real cookies. Plain HTTP development-mode test server with fixed nonsecret test SESSION_SECRET, APP_MODE=demo and PUBLIC_ORIGIN=http://localhost:<testport> is allowed. Separately assert production HTTPS cookie flags using controlled HTTPS/proxy tests; don't call an HTTP cookie test proof of production Secure behavior. Reconcile existing frontend tests that intercept only /chat with the new session/capability prerequisite. Keep production-mode CSP checks independently. A test env NODE_ENV=test must not silently skip starting its local webServer; choose a documented startup entry/config rather than hanging.

The inherited cache-under-50ms test is intermittent and is not an API correctness assertion. Replace that unit assertion with deterministic cache-reuse evidence (cached chunks require zero re-embedding and initialize without duplication), preserving the intent rather than raising the time limit until green. Keep optional performance measurement separate from correctness tests. Cache model-awareness/relevance/source metadata remain later work.

Acceptance: no real action can dispatch; support never simulates on provider failure; demo is explicit and makes no provider request; one browser cannot select another browser's history/usage with a body ID; session expiry/reset and parallel requests are bounded and fail visibly; requests time out through body parsing; public errors/logs contain no raw upstream secrets; existing visual/keyboard/reduced-motion checks pass. Report actual commands, counts, screenshots, process exit and unverified limitations. No self-awarded production-ready claim.

Environment/deployment docs list APP_MODE, PUBLIC_ORIGIN, SESSION_SECRET, single-process store, restart expiry, HTTPS and proxy requirements. Never write real secrets to docs/receipts, change production settings, or assume Render has configured new variables. This phase prepares a branch; the user controls deployment after review.

## Builder discretion and later work

Builder may choose internal helper filenames and exact test fixtures within the subsequent plan, and a maintained equivalent store if memorystore proves unsuitable after inspection, with an explicit documented review. It may not choose to enable tools, use browser-supplied identity or silently weaken cookies/origin validation.

Future client-action phase must select a real customer identity source, integration, permissions, confirmation, idempotency and audit contract. Future answer-quality phase adds source metadata, relevance calibration, model-aware indexing and an evaluation corpus. This foundation does not substitute for either.
