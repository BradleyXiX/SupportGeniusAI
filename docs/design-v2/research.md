## Motion and runtime decisions

Use progressive enhancement. [web.dev's reduced-motion guidance](https://web.dev/articles/prefers-reduced-motion) supports adapting nonessential movement to the user's preference. The reference displays SVG first and fetches its native WebGL module only after an explicit enable action; reduced motion keeps the poster. It listens for preference changes, visibility, intersection, and context loss.

[web.dev on animation performance](https://web.dev/articles/animations-and-performance/) explains the cost of layout and paint. Local feedback uses opacity/transform or color transitions with bounded durations. One renderer owns the point sculpture. No smoothing library or React state loop is required. Local tests are lab evidence; [Core Web Vitals](https://web.dev/articles/vitals) require field data for field claims.

The prototype uses true WebGL point geometry rather than a raster animation or a 2D status indicator. It is intentionally a small custom module: this satisfies the specific visual without a framework or 3D dependency. Three.js becomes appropriate only if a later scoped asset requires lighting, model loading, or more advanced interaction. Do not add it solely for a sphere. Blender is optional if an original asset improves the concept; no asset slot blocks the layout.

## What professional READMEs actually need

- [Resend's Node SDK README](https://github.com/resend/resend-node): concise purpose, install/use path, and direct developer documentation. Transfer the shortest route to a useful result. An SDK's minimal README is not a reason to omit application operating limits.
- [Cal.diy's current repository](https://github.com/calcom/cal.diy) (the former `calcom/cal.com` URL redirected here during review): visual identity, product framing, setup, contribution/community and licensing information. Transfer clear navigation and real project imagery, scaled down for this smaller application. Do not copy enterprise badges, a license, infrastructure, or contribution promises the project does not have.

Recommended SupportGenius README order: brand → one-sentence purpose → actual console screenshot → current capabilities and boundaries → five-minute deterministic demo setup → a small Mermaid architecture diagram → test commands → production/deployment limits → contribution/docs → license status. Use relative image paths stored in the repository so forks and branches render correctly. Keep the concept screenshot in a clearly labelled design-reference subsection. No decorative badge wall, unsupported uptime metric, fake CI badge, or invented download count.

Detailed provider configuration belongs in `docs/deployment.md`, avoiding repeated stale pricing tables on the front page. Screenshots must name route, commit, viewport, and mode in a nearby caption or manifest, contain no secrets/customer data, and be refreshed when the UI materially changes. Mermaid helps explain the actual request path, not a hypothetical multi-tenant platform.
